# v0.9.4 — TCP packet diagnostics

v0.9.3 finally opened upstream TCP connections:

```text
protect returned false; binding underlying network
tcp connected :443
```

But the phone still has no internet, so the remaining failure is in the TCP packet relay or DNS. This build logs enough to identify exactly which.

## Added diagnostics

- First 6 TCP packets per flow: flags, sequence, acknowledgement and payload length.
- SYN-ACK bytes in hex, so the IP/TCP header and checksum can be validated offline.
- First remote TCP payload: length, sequence and acknowledgement.
- DoH sockets now bind to a non-VPN network when `protect()` returns false, matching the TCP fallback.

## What the next log will show

After installing v0.9.4 and enabling both switches:

- `tcp flags=2 ...` — app SYN.
- `tcp synack hex=...` — our SYN-ACK. If the app never sends an ACK/data after this, the SYN-ACK header/checksum is invalid.
- `tcp flags=16 ... len=0` — app acknowledged the SYN-ACK.
- `tcp flags=24 ... len=...` — app sent TLS ClientHello data.
- `tcp remote data len=...` — the server replied.
- `dns ... response=...` — DNS reply size or SERVFAIL.

That distinguishes:

1. SYN-ACK rejected by the phone (no ACK/data after `synack`).
2. App data received but not relayed (no `remote data`).
3. Server data received but not delivered back to the app.
4. DNS returning SERVFAIL (`response` equal to query size).
